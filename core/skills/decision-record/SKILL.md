# decision-record

## Rules

A session forgets everything when it closes. A decision that lives only in the
chat is re-litigated by the next session, and sometimes reversed, because
nothing told it the question was already settled.

`specs/_decisions.md` is the repository memory. It is injected at session start
alongside `specs/_context.md`, so every session begins knowing what previous
ones decided. `_context.md` holds facts about the code; `_decisions.md` holds
choices about it. The two are kept apart because facts are regenerated by a
script and choices are not.

Record a decision when it **constrains future work**: an approach chosen over an
alternative, a convention adopted, a trade-off accepted, a thing deliberately
not done. Do not record what the code already says.

Every entry carries the alternative that was rejected. A decision with no
rejected alternative was not a decision, it was a default, and it will not
survive the first person who prefers the other option.

**Graduation.** When the same decision is cited in three sessions, it has
stopped being a decision and become a rule. Promote it to the instruction file
whose `applyTo` matches, and leave a one-line pointer in its place. Memory that
never graduates grows until nobody reads it.

Anti-patterns to refuse:

- recording what was done rather than what was decided
- an entry with no rejected alternative
- superseding a decision by deleting it. Mark it superseded and point forward
- letting the file exceed a screen without graduating anything

## Workflow

1. At the end of any phase that settled something non-obvious, name the
   decision in one sentence.
2. Write the rejected alternative and the reason it lost.
3. Append the entry, dated, with the session id that made it.
4. If a prior entry is now superseded, mark it so and link the new one. Never
   delete.
5. When a decision is cited for the third time, promote it to the matching
   instruction file and replace the entry with a pointer.

## Output

```markdown
## 2026-09-03 · export follows the active filter, not the table

Session: 007-export-csv

Rejected: exporting the underlying query. It is what the report shows, but the
table passes a million rows and finance wants what they filtered to.

Constrains: any future export or download feature uses the filter state as its
input. If someone needs the whole table, that is a separate, explicitly named
feature.
```

```markdown
## 2026-07-12 · retries use exponential backoff with jitter

Superseded by 2026-09-01 · retries are the responsibility of the gateway
```

## Validation

- [ ] The entry states a decision, not an action.
- [ ] The rejected alternative and the reason are written down.
- [ ] It is dated and names the session.
- [ ] Anything it supersedes is marked, not deleted.
- [ ] Nothing cited three times is still in the file instead of an instruction.
